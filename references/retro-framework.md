# 复盘方法论细则

配套 `SKILL.md` 使用。回答三个问题：**挖多深才算够**、**怎么判真假**、**沉到哪一层**。

---

## 一、四层深度：判定标准与坏例

### L1 事实层 — 目标和实际差多少

**合格**：能用数字或明确的观察描述差异，且能指认是哪一步造成的。

| | 内容 |
|---|---|
| ✅ 好例 | 「要求 3 根柱/月 + 年份筛选，实际交付了，但精确 16:9 时 KPI 被媒体查询误降为 2 列——因为我用 `max-aspect-ratio:16/9`，而 1600×900 恰好命中该条件」 |
| ❌ 坏例 | 「整体完成得不错，布局还需要优化」 |

**自检**：这句话能不能贴到别人面前，让他独立复现同一个判断？不能就是坏例。

### L2 归因层 — 根因属于哪一类

必须四选一，不许写「沟通不畅」「时间紧张」这种无法对策的糊话：

| 根因 | 含义 | 对策方向 | 典型信号 |
|------|------|----------|----------|
| `信息缺失` | 当时根本不知道 | 补上下文 / 先问清楚 / 先做数据盘点 | 「我不知道表里有备注行」 |
| `判断错误` | 知道但判错了 | 改判据 / 加决策清单 | 「我知道有 16:9 要求，但以为该断点安全」 |
| `执行失误` | 判对了但做错 | 加校验 / 自动化检查 | 「知道要过滤，手写脚本时漏了」 |
| `工具缺陷` | 流程对但工具卡住 | 换工具 / 加兜底通道 | 「git push 一直 502」 |

**关键判据**：同一根因在本次任务中出现 **≥2 次**，说明是流程缺陷而非偶发，必须升级为 Skill 类或提示词类沉淀。

### L3 迁移层 — 下次同类任务第一步做什么

**只写一句，且必须是可执行的第一个动作**，不能是原则。

| | 内容 |
|---|---|
| ✅ 好例 | 「先跑一遍 `check_report.py` 静态体检，再截图看布局」 |
| ✅ 好例 | 「先读 xlsx 的第 1 列空值分布，确认有没有非数据行」 |
| ❌ 坏例 | 「注意细节」「提前规划」「多沟通」 |

**自检**：下次开工时，这句话能不能直接作为第一个 tool call / 第一个动作？不能就是还没落地。

### L4 元改层 — Harness 哪一环该改

| 现象 | 该改 | 不该改 |
|------|------|--------|
| 反复说同一类要求 | 记忆（memory） | — |
| 反复走同一套流程 | 技能（skill） | — |
| 输出结构总不对 | 提示词（prompt） | — |
| 想清了但还没成型 | 改进手册（manual） | — |
| 模型能力不够 | — | 这四项都改不了，别硬沉 |

## 二、证据闸：怎么算「有结果支撑」

一条 finding 或候选进页面的前提是 `evidence` 非空，且满足以下**任一**：

1. **可指认的产物**：文件路径、截图、check 脚本输出、提交哈希
2. **可复现的现象**：换分辨率就翻车、换数据就报错——能说清触发条件
3. **可对账的数字**：1249 行里剔出 2 行、3 月 656 条是次中位数 4 倍以上

**不算证据**：
- 「感觉」「一般来说」「按惯例」
- 「用户可能会喜欢」——除非用户真说过
- 「业界最佳实践」——除非本次任务验证过

`confidence` 填写规则：

| 值 | 条件 | 页面表现 |
|----|------|----------|
| `high` | 本次任务已跑通 / 已验证 | 正常显示 |
| `medium` | 推理合理但没验证 | 标黄「待验证」 |
| `low` | 凭直觉 | **不入页**，脚本会告警 |

## 三、范围判定树：沉到哪一层

```
这次经验，下次还会用到吗？
├─ 不会（一次性） ──────────────► scope=single
│    沉淀上限：1 条，且只允许 prompt 类
│    （单次任务往长期记忆里塞东西，是最常见的污染源）
│
└─ 会
   ├─ 只在某一类任务里会用到 ───► scope=recurring
   │   主力：memory（口径/事实）+ skill（流程）
   │
   └─ 跟具体领域无关，换任何任务都成立 ─► scope=cross
       主力：manual（方法论）+ 全局 memory
```

**交叉检验**：`scope=cross` 的条目，必须能举出一个**不同领域**的应用场景。举不出来的，实际只是 `recurring`，别往上抬。

## 四、Harness² 差异对比台

用于**有多方案**的场景。填入 `variants`：

```json
{
  "variants": {
    "question": "本次对比的核心问题（如：单文件内联 ECharts 还是 CDN 引用？）",
    "dims": ["离线可用", "文件体积", "构建耗时", "可维护性"],
    "list": [
      {"name": "A. CDN 引用",   "scores": ["否", "12 KB", "快", "易"],
       "note": "断网即白屏，用户场景不可接受"},
      {"name": "B. 内联 ECharts","scores": ["是", "1.04 MB", "慢 3s", "需重建"],
       "note": "离线可开，体积可接受"}
    ],
    "verdict": "选 B。离线可用是硬约束，其余维度均可接受。组合方案：内联但压缩到 gzip 后 280 KB。"
  }
}
```

**填写要点**：

- **不比绝对分，比差量**。「A 得 85 分、B 得 90 分」没有信息量；「B 在离线维度胜出，代价是体积 87 倍」才是。
- **维度要包含代价**，不能只列好处，否则是自证。
- **`verdict` 必须给结论**，不写「各有优劣，看情况」——那是没结论。
- 只有一个方案时**整块省略**，不要造数据凑对比。

## 五、六种思考方向：什么时候用哪个

| 方向 | 适用任务类型 | 产出归类 |
|------|-------------|----------|
| 结果对照 | 有明确交付要求的（开发、报表、文档） | L1 |
| 有效做法 | 全部 | L1 → memory/prompt |
| 弯路根因 | 出过返工 / 试错的 | L2 → skill/manual |
| 决策分叉 | 中途换过方案、纠结过的 | manual |
| **迁移边界** | 全部（最常被跳过） | manual |
| 元层反思 | 全部 | L4 |

### 迁移边界：为什么单列

多数复盘只问「这条经验成立吗」，不问「它在什么时候不成立」。

例：「明细表必须按业务字段白名单过滤」——成立。但边界是：**当业务字段本身可能为空或新增枚举值时，白名单会静默丢数据**。所以配套要做的是"过滤计数 + 丢弃原因打日志"，而不是无条件白名单。

**不写边界的经验，用一次就会伤一次。**

## 六、条数闸：为什么是 5 条

第二张图的约束值得照抄：*每条一句话，总共不超过 5 条；没把握的不写*。

理由不是"精简美学"，而是**下次开工时谁能读完**。复盘笔记的消费场景是「开工前扫一眼」——那个场景的时间预算是 30 秒。30 秒读不完的笔记，等于没写。

**口径要点**：「下次第一步」在成品笔记里本身就是一条（见下方成品形态的第 5 条），所以：

```
有效做法(≤3) + 弯路(≤2) + 下一步(1) ≤ 5
→ 实际上 worked + detours ≤ 4
```

`gen_retro.py` 的闸门按这个口径计算；只写 3 做法 + 2 弯路时合计已是 6，会告警。

超限时的正确做法**不是删内容，而是往下拆**：
- 5 条装不下 → 说明有两类不同任务混在一起复盘了 → 拆成两次复盘
- 单条写不进一句话 → 说明还没想透 → 回到 L2 重新归因

## 七、反面清单：这些别写进候选

- ❌ 「加强沟通」「注意细节」「提前规划」——无对策动词
- ❌ 「使用最佳实践」——哪个实践？谁的最佳？
- ❌ 「下次要更仔细地检查」——检查什么？怎么查？
- ❌ 把**任务描述**当经验（「本次处理了 xlsx」不是经验）
- ❌ 把**工具自带能力**当发现（「openpyxl 能读 xlsx」不需要沉淀）
- ❌ 一条候选混装两个改动（改流程的同时改语气），用户无法判断勾不勾

## 八、复盘笔记成品形态

「复制复盘笔记」按钮输出的格式，直接对应图片 2 的模板：

```
这次任务结束了，留一份笔记给下次的我：

任务：【一句话描述这次的任务】

1. 管用的做法：xxx（依据：xxx）
2. 走过的弯路：xxx → 下次避开方式：xxx
3. 下次第一步先做：xxx

（共 3 条；没把握的已剔除）
```

这个格式的消费方是**下次的自己**，所以：第一人称省略、去掉背景铺垫、每条独立可读。
